## ADDED Requirements

### Requirement: 批次展示独立于事件连接阶段

客户端 MUST 根据当前已有的批次临时进度保持执行卡片与顶栏状态，不因事件流失败将会话切为 ready 而隐藏仍在运行的批次展示。展示判断 MUST 为纯投影，不创建新的业务状态、消息、持久记录、自动播报、外呼或停止请求。

#### Scenario: 来电期间断流后返回当前页
- **WHEN** 多路外呼过程中页面进入 inactive / paused，事件流失败，返回前台后原批次仍运行
- **THEN** 同一位置仍有一张执行卡片，顶栏显示执行或核对状态，不能回落到待命；原业务正文、真实思考、候选身份和输入准入不被改写

#### Scenario: 补查恢复逐路可信状态
- **WHEN** 原有补查返回可信的正在拨打或通话状态，而页面仍为 ready
- **THEN** 执行展示持续存在，顶栏不因不再存在 VERIFYING 项而回落待命，不重复外呼；全部路由已结束但汇总未就绪时显示结果整理

#### Scenario: 已停止批次与历史重进
- **WHEN** 用户停止原批次并退出再恢复同一任务，停止已受理但可信结果尚未返回
- **THEN** 保留既有任务处理进度与三点禁用门禁；同一次停止不重复发送，明确失败项仍可显式重试，历史入口不重新执行工具

#### Scenario: 观察耗尽仍无可信结果
- **WHEN** 原有有界补查耗尽并留下结果待核对的临时批次卡
- **THEN** 原位置以静态未确认说明取代加载动画，保留原有只读补查和停止门禁，不延长轮询或伪造最终结果

#### Scenario: 可信终态撤销执行占位
- **WHEN** 同一批次的可信结果通过进度或账本到达
- **THEN** 执行占位与运行顶栏撤销，结果和真实思考保留原身份与位置，不将结果已读回执失败视为批次未结束；其他批次、旧回调与真实执行错误不冒充当前结果

#### Scenario: 双端一致与普通任务隔离
- **WHEN** Android 或 iOS 使用相同批次事件，或普通会话没有活跃批次
- **THEN** 两端使用相同 Dart 展示规则；普通任务、真实错误、结果整理与语音输入 / 播报的既有优先级保持，不为静态历史结果新增运行卡片
