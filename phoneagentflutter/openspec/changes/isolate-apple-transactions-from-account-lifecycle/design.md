# 设计与职责

Flutter 基线 feature/test_v1.8.0@26ce44a09f9a7b1f6ebffd562d7c8b8722b19505；SDK 基线 feature/test_v1.8.0@1a1bf12ef4d512fbf9e699f6c1282727e442e817。开始时工作区均干净，不切分支，不部署，不执行数据库写入或真实支付。

## Owner、入口与身份

- SDK Controller 负责 C1 应用身份；增量 `/api/commerce/apple/reconcile` POST 不依赖用户 Bearer。Service 验证 Apple 签名/环境/商品/token，定位原 attempt/order，复用 operations.accept 与原有幂等/账务事务。仅返回 transactionId、paymentState、fulfillmentState、finishAllowed，无账号、订单、金额或权益信息。
- 原 `/apple/transactions` 仍按登录账号校验订单所有权，不扩大普通账户接口权限。补单不得创建订单、改归属、撤销注销或使账号 ACTIVE。
- Flutter 应用级 Apple 协调器持有环境/SDK 地址作用域的加密证据队列，复用现有原生 updates/unfinished/acknowledge。登录、退出和本地 identityEpoch 不销毁交易工作；账号 controller/runtime 只管理当前账号 UI、购买尝试与取消上报。
- 独立协调器是新客户端唯一 finish owner，须原服务端付款及履约均 SUCCEEDED 才允许 finish；未知、异常、网络失败保留工作。持久化完成后才处理、finish 成功后再删队列，重复证据/响应丢失均幂等。有界重试，重新前台/网络/交易事件可再尝试，不轮询用户界面。
- 同 SKU 预检发现外账号原交易时仅完成原交易；原处理成功后继续本次购买，不向当前账号展示原账号订单或误报本次支付成功。仍未处理完则暂不创建新订单，保留真实失败语义。
- 原生购买弹窗不增加超时取消；不新增恢复购买入口、对话框、退款或注销门禁。

## 支付材料与历史版本

认证过滤器从已签名 v1/v2 token 取得账号与 auth_epoch，v1 等价 epoch=0。支付材料事务取得既有钱包/订单锁后复核 ACTIVE、enabled、deleted 与同一已验证 epoch。受理/撤销/最终注销仍递增 epoch；正常切换、升级或登录不新增递增规则。普通支付 API 不新增必填请求字段，保持 v1/v2 格式。

此门禁只在新支付材料授权路径（包括 Android 支付宝原单重试），不用于 Apple/支付宝回调、既有验单、履约、退款和结算。不改历史订单、token、金额映射或现金投影。旧客户端不获得新增独立补单能力；必须区分接口兼容测试与旧安装包真实验证，不能承诺所有历史版本已验证。

## 文件与微批

客户端 domain 定义补单结果/队列端口；data 负责 C1 网络和加密存储；独立 controller 负责交易发现/串行化/重试/finish；providers 接线和当前账号刷新。保留既有 PurchaseController 超限例外，新增流程不堆入它。每个手写逻辑微批最多3文件；文档/机械格式化单独记录。
SDK 新 Controller/Service/DTO 分层；认证代次通过可信 request attribute 传递至材料事务，不信任客户端新增字段。不改公共任务编排标记区域；相邻保持 DEVICE-01、ENTRY-03、HISTORY-01。

## 回放与验证边界

APPLE-LIFE-01 A购买后退出/B登录；02 A冷静期/最终逻辑删除后迟到；03 同SKU原交易预检；04 服务端处理中不finish，完成后仅一次；05 断网/丢响应/进程重启/finish失败；06 注销/撤销与材料并发，旧epoch不得重获材料；07 v1/v2及Android原材料/回调合同；08 无交易与发现/单笔失败区分，成功补单刷新当前账号权威权益。

本地定向单测、静态检查、模块编译证明程序分支与接口合同，不代替真实 MySQL 锁竞争、历史安装包或 Apple Sandbox/真机。后端增量先发布再启用新客户端；本次不执行发布。

## 实现补充

- 支付材料的可信 principal 只在原 POST `/orders/{orderNo}/payment` 中携带，不改变其他业务过滤器的 `verify` 调用合同。旧 v1=0 与 v2 epoch 均由签名 token 提取，不读取客户端自报 epoch。未修改数据库结构。
- 原生 `Transaction.updates` / `unfinished` / `finish` 实现未改；Dart 应用协调器复用原通道。它的发现路径不以 `canMakePayments` 过滤原交易，新购买仍按原权限检查。旧原生购买等待不设超时；协调器自己的发现/存储/验单等待有界，并在环境作用域销毁时撤销本地 deadline；已发网络、原生购买和实际 finish 不伪装取消。
- 队列每个环境/SDK地址最多512个不同交易，达到上限写入失败，不丢旧证据、不提前finish；相同ID串行化，同签名版本共享处理中/失败结果，新签名版本单独核验。自动重试为2/10/30秒，预算耗尽等下一次前台、网络或原生交易事件，不无限轮询。
- 服务端处理完成后先完成 StoreKit，再清持久队列；重启时若服务端已确认完成且一次成功的 unfinished 枚举没有该交易，仅清本机任务，不伪造一次 finish。换 Apple ID 后重新发现的未完成交易仍重新处理，缺席不缓存为“已finish”。发现失败、权限未知或服务端未完成时不按缺席清理。
- 跨账号原交易在购买中返回时，只结束新单本地流程；新单已独立付款仍展示它自己的真实成功，关闭失败继续可查询，不自动重开购买或改归属。仅使用原共用反馈组件显示中性结果。
- 补单完成事件不携带账号/订单；当前登录的积分、会员和模型目录分别重新查权威数据。会员刷新保留商品、原生价格、用户选择与协议状态，迟到结果不能覆盖换账号/销毁后的控制器。
- Sandbox补单范围沿用明确启用的生产应用兼容配置，不依赖“开启新销售”的开关；既有金额、退款/撤销处置与幂等都由原服务处理。真实异常或退款处置未完成时仍不finish，需按原售后流程处理。
