# Design

## 机制与证据

`ConversationStopCoordinator` 当前 busy 能挡住在途重复回调，但受理后的10次同步耗尽会释放 busy；`notice` 进入 state.notice 后被 ConversationPage 的 timeline feedback 渲染，completed 未清理。accepted 的 activity 还会生成思考占位。诊断 zip 只读筛选白名单 operation/result/time/statusCode/elapsedMs，匹配内容仅为 voiceMedia 生命周期，缺少可证明 stop API 与终态顺序的现场日志；本次只签收可复现源码机制和自动回放。

## 文件职责与状态 owner

- `conversation_stop_coordinator.dart`：停止请求在途/受理/显式重试及有界只读同步，沿用 revision 隔离，不增加第二套业务终态。
- `conversation_stop_binding.dart`：停止与会话状态的接线，独占本次 transientStatus 生命周期，按原 command / batch 终态撤销暂态；不清业务正文或其他模块 notice。
- `conversation_state.dart`：增加独立暂态字段并按现有 copy 传递。
- `conversation_controller.dart`：仅在现有消息投影后调用 stop 的终态协调。
- `conversation_status_presentation.dart` / `conversation_page.dart`：顶部协调当前暂态与已有重试动作；原思考占位位置复用同一张展示卡承接停止、等待结束、整理结果，标题为“任务处理进度”，不伪装为真实 AI 思考。现有 recovery 错误、真实音频异常和结果整理优先。
- 独立定向测试：真实 Controller + 页面连续点击、超时未决、迟到终态、失败重试；外部网关/停止/历史以受控端口替代。

每个文件沿用原职责；新字段解决展示通道，停止 owner 决定生命周期，不把网络或终态判断塞进页面。未来其他操作可使用相同顶部状态字段，但本次不批量迁移或吞掉已有技术错误。

## 连续停止进度（本次批准）

复用停止 owner 的在途与已受理未结算状态，区分网络请求 busy 与展示上的等待结果。首轮十次只读同步结束不是业务完成：底部按钮继续禁用，顶部保留只读同步入口；明确停止失败或部分失败保留显式重试。真实终态、失效与有界恢复耗尽沿用原 owner 收尾，不新增轮询或第二套状态机。

退出再进入时，页面控制器会销毁，恢复接口只给 activeBatchId 而没有停止受理字段。因此由账号生命周期持有本进程内的批次停止请求状态，按账号 / session / batch 隔离；确认停止并发送 stopBatch 时登记在途，回执后更新。恢复时先用账本可信终态清理对应记录，再为仍活跃的同一批次恢复“请求在途”“已受理待结果”或“明确部分失败可重试”。未登记停止状态的活跃批次继续允许首次停止。该记录只恢复交互门禁，不充当业务终态；进程被杀后的跨启动恢复仍需服务端持久停止状态支持。

请求在途时由同一账号作用域持有原 stopBatch Future，并登记待回执状态。页面关闭只失效旧页面的展示回调，不取消请求结果记录；新页面读取待回执状态并订阅该批次结果。回执成功后转为已受理或部分失败，明确网络失败时释放为可重试；可信终态先到时清理记录，迟到回执不得复活旧状态。只有本批次监听者接收更新，不向新命令或其他账号写页面状态。

进度卡沿用原卡宽度、圆角、颜色、动画和 timeline slot，固定同一展示 key，只更新阶段文案。等待结果优先显示整理结果；停止在途立即显示停止进度。真实思考卡及正文保留，临时进度不进入消息账本、历史或 TTS；结果就绪后撤销临时卡，不等待评分或录音。底部蓝色按钮的圆形底色、尺寸、布局不改；语音播报中断继续走原有独立控制。

底部停止控件禁用时沿用原圆形底色与尺寸，图标改用现有三点处理中动画；实际点击回调仍为空。动画表达停止请求在途或已受理后等待结果，不代表业务终态；减少动态效果的系统设置下显示静态三点。

有界观察耗尽而结果仍未确认时，复用既有 batchUnconfirmedNotice，将同一卡片转为静态未确认说明、停止加载动画，避免无限假处理；该说明不再重复显示为卡片外技术正文。原批次身份、发送门禁和只读同步保留。合入远端 `e4f99715` 的未确认合同后，相关旧测试改为断言 VERIFYING 临时进度而非 UNCLEAR 终卡；不改变该远端业务实现。

## 验证与边界

2026-10-21 测试环境同会话在 20:02:15 提交的批次结果为 `PENDING / EXECUTION_ERROR`，其中一路 `UNCLEAR`，SDK 仍为 `CANCELLING / PREPARED`；这只证明编排异常已写入账本，不证明该路物理结束或账务结算。客户端保留错误回执及既有 `isRunning` 展示语义，另以 `BatchReceipt.stopSettled` 判断已受理停止是否可以清门禁：执行错误不得视为停止结算。停止 owner 的历史、进度读回及跨页恢复在有已受理停止时使用该谓词；未受理停止的普通错误回执仍按既有技术结束语义展示，不重新开放停止。前台恢复仅在已受理停止时不以错误回执清除待核对反馈。`BatchProgressTracker.isFinal` 继续承载错误回执的既有展示与流结束语义，不把错误事实隐藏为成功。后端已提交错误结果不可由客户端改写，实际补全仍依赖服务端安全恢复与现场验证。

先 RED 再最小 GREEN。重复点击同一停止在途只1个请求；受理后未决重试只读同步，部分失败/真实失败可显式重试；所属终态清除暂态，其他任务终态或旧回调不能清当前状态。Android / iOS widget 核对顶部与时间线归属，不等于真机或真实后端验收。
