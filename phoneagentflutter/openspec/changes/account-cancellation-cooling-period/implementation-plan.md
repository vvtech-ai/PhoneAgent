# PhoneAgent 账号注销详细实现方案

日期：2026-10-26。状态：核心源码已实施，未部署；最终接口以api-contract-proposal.md为准，真实环境验收仍待完成。

## 1. 目标、依据与范围

用户本次明确要求优先，其次为附件协议和需求页 https://agent.vvtech.tech/cancel 。入口固定为“设置 → 关于PhoneAgent → 账号管理 → 注销账号”。网页旧入口按用户指定覆盖；2026-10-28用户确认最终正文按需求原文保留“再次登录自动终止”，这里“再次登录”指用户明确继续登录并成功完成撤销及登录，实际撤销门禁保持。

交付覆盖：Flutter Android/iOS、SDK账号服务、Agent/媒体等业务准入、权益与逻辑删除及资源失效、协议发布、自动回放及真实联调。无需新建须知页、成功页或进度页，不增加协议勾选框，不新增会员暂停、延期、补奖励或自动退款规则。

本方案不会执行真实注销、短信、支付、部署或用户数据删除。

## 2. 用户流程与文案

### 2.1 两阶段确认与申请

1. 点击入口恢复“确认注销账号？”提示，取消/关闭不发短信。
2. 确认后发送绑定手机号验证码，沿用Flutter共用6格输入、脱敏号码、正式频控；按服务端重发倒计时显示禁用/可用状态，反馈统一Toast。
3. 完整输入6位且组词结束后自动调用sms/verify，无验证按钮；接口只验证本人，返回10分钟一次性verificationToken及最终确认数据，不创建申请。
4. 验证成功展示“注销账号”最终确认框，含服务端预计完成时间和内联协议，无勾选框或文字输入；取消/关闭清空输入并返回验证页，不受理；再次输入完整6位重新验证。
5. 最终点击“注销”才携verificationToken调用applications；只有服务端受理成功才退出登录并在中央显示约2秒“已提交注销申请”。
6. 验证凭证只驻内存，不写恢复存储；最终提交前保存原操作和查询信息，丢响应按原操作查询。

最终确认正文按2026-10-28批准模板逐字展示：“点击注销后，账号将在 {完成时间} 完成注销。期间若再次登录，注销流程将自动终止。继续注销，即视为你已阅读并同意《PhoneAgent 账号注销协议》。”完成时间动态取本次服务端确认快照、按北京时间显示到分钟；不追加期限时长或其他扩写。用户定义的“再次登录”仍须明确继续登录并通过服务端撤销门禁。预计时间不提前起算冷静期，实际截止仍由服务端受理确定。参见[流程图](flow.md)。

### 2.2 冷静期再次登录

完成原账号短信身份验证后先显示：

> 账号正在注销中
>
> 你已提交账号注销，将于 {完成时间} 正式注销。若继续登录，注销流程将自动终止。

按钮“保持注销 / 继续登录”。保持注销为灰底红字，继续登录为黑底白字，背景保持原登录页。

- 保持注销、关闭、返回：仅关闭本地提示，不调用撤销、不进入首页、不改变截止。
- 继续登录：提交明确撤销命令；只有服务端成功且本地正常保存登录会话后才进入首页。
- 撤销失败：保留可理解的失败提示；未知结果按原操作查证，不先进入首页。
- 验证凭证过期：重新验证本人，不自动再次撤销。
- 截止后：不能撤销或恢复原数据；同手机号重新注册策略待明确。

## 3. 状态模型与时间边界

账号生命周期建议：ACTIVE → CANCELLATION_PENDING → CANCELLED。CANCELLATION_PENDING仅在服务端当前时间严格早于effectiveAt时可显式撤销回ACTIVE。

申请记录独立状态：PENDING / REVOKED / FINALIZED；清理作业独立状态：QUEUED / RUNNING / RETRY_WAIT / COMPLETED / MANUAL_REVIEW。清理失败不把账号改回ACTIVE，不覆盖业务上的最终注销状态。

| 当前状态 | 事件 | 条件 | 结果 |
| --- | --- | --- | --- |
| ACTIVE | 受理申请 | 本人验证、协议版本和在途检查通过 | PENDING，受理时间+15×24小时为截止 |
| PENDING | 身份验证/保持/关闭 | 任意 | 不变，不发普通凭证 |
| PENDING | 明确撤销 | 数据库裁定now < effectiveAt | REVOKED，账号ACTIVE，生成新会话 |
| PENDING | 到期 | now >= effectiveAt | FINALIZED，账号CANCELLED，排入清理 |
| CANCELLED | 撤销/旧凭证访问 | 任意 | 拒绝恢复 |
| ACTIVE | 撤销后重新申请 | 新验证、新操作 | 新申请新截止 |

使用服务端数据库或统一可信Clock计算时间；事务内取得锁后重新取时间，不能使用排队前旧时间通过边界。相等时按到期处理。即使worker尚未执行，鉴权/撤销也必须按effectiveAt拒绝恢复。

## 4. 状态owner与数据结构

账号生命周期由SDK账号领域拥有；不把注销逻辑塞进支付控制器或Flutter SessionController。新增名称为建议，具体迁移遵循仓库惯例。

- user_account：新增 cancellation_state、auth_epoch；enabled继续表示既有封禁等管理状态，撤销不能解除封禁。
- account_cancellation：application_id、account_id、request_id、status、accepted_at、effective_at、revoked_at、finalized_at、agreement_version、agreement_digest、version。
- account_operation：操作类型、账号、稳定operation_id、请求摘要、状态、结果引用。相同ID不同参数拒绝；查询不能把“不知道”当“未受理”。
- account_cancellation_challenge：账号、登录代次、用途、有效期、尝试计数、消费状态；验证码/凭证只存合适的摘要或受保护记录，不存诊断日志。
- cancellation_cleanup_job/outbox：账号、申请ID、步骤、租约、重试时间、错误分类、完成水位；不带原始用户正文。

强制约束：同账号最多一份有效PENDING；(account_id, operation_type, operation_id)唯一；清理步骤(application_id, step)幂等。所有相关写入采用一致账号锁顺序，并用版本条件防迟到更新。

受理、撤销和到期变更在本地数据库事务中写状态与outbox；跨服务动作不能靠数据库事务假装原子完成。数据库选型及现有迁移规范确认后决定唯一索引实现。

## 5. 实施接口

## 6. 后端执行细节

### 6.1 受理事务与在途业务

验证凭证先校验，再锁账号，核对ACTIVE、封禁、协议版本、同操作重放、在途状态。已提交的同操作应先恢复原结果，不能因验证码已消费而拒绝合法重试。消费凭证与创建申请必须同事务成功。

在途检查不能“先查无任务，稍后写申请”，否则并发新任务可穿过。普通业务准入与注销受理应共享账号准入版本/锁或租约：受理先关闭新准入，再核对旧活动租约；有真实通话/任务/支付未终结则拒绝并恢复本次关闭操作，或进入有界准备步骤但不得报告已受理。具体选择复用现有准入设施后决定，不能自动取消用户任务或扣款。

明确提交成功时，在同一事务写申请、lifecycle、auth_epoch和outbox。截止固定为acceptedAt+15天；重复提交不延长。

### 6.2 全设备访问与旧token

SDK verify/renew、Agent SSE鉴权、媒体票据签发、SIP/翻译准入、旧恢复入口均接入同一生命周期判断。只改SDK filter不能证明所有路径已阻断。

建议受理及撤销分别推进auth_epoch，新token含签发代次；旧token在撤销后仍不可复活。旧格式token兼容需单独定义：新字段迁移不能立即误踢全部正常账号，也不能允许曾注销账号旧token复活。账号级撤销时间或legacy禁用标志可作为过渡，按签发格式审计后定稿。

REST逐请求检查；已建立的SSE/WS按账号状态事件失效并停止新操作，票据入口重新校验。缓存失效需定义最大窗口；关键外呼/支付以权威准入判定为准，不能在注销后借缓存继续执行。

### 6.3 登录与撤销

SmsLoginService先验证身份，再分流生命周期，之后才执行普通登录副作用。覆盖验证码、邀请挑战、审核/固定测试码和referralReplayStore重放路径。公开登录接口不应在本人验证之前暴露手机号是否正在注销。

冷静期不能调用points.activateSession、正常发token或发奖励。撤销成功后复用普通登录收尾，保持原幂等奖励策略；是否有当天合法奖励由原规则决定，不额外补发。

撤销与到期锁同一账号/申请，事务中比较截止、申请版本和精确ID。另一轮新申请不能被旧challenge撤销。撤销不会恢复过期会员或回滚真实结算。

### 6.4 到期逻辑删除及后续处理

worker按effective_at索引分页领取，带租约和有界批次，多实例可安全并行。同账号到期操作幂等：先逻辑最终注销并落清理outbox，再异步执行跨服务清理。中途崩溃从步骤水位续跑。

最终注销采用逻辑删除：账号标记CANCELLED并记录deleted_at，不硬删除账号行，不默认批量物理删除业务表、录音、附件或供应商资源。原账号及业务数据对用户不可见、不可访问、不可恢复；管理封禁与逻辑删除保持独立。

逐域核对任务/对话/字幕、录音附件、翻译历史、联系人、记忆、音色/克隆资源、设备绑定及设置的访问路径。查询、导出、下载、签名URL签发、缓存、媒体票据均须排除逻辑删除账号；既有下载链接需评估失效机制。不能只过滤账号列表而继续暴露业务数据。

异步作业负责账号资源解绑、访问撤销、权益终止及审计核对。个人信息留存、匿名化或物理清理属于独立的数据治理范围，按既有政策及明确清单执行，不作为本需求默认新增硬删除动作。备份恢复不得清除注销标记；共享资源不得误伤其他账号。

权益终止采用独立原因/流水类型，不能记为通话消费。支付、退款、奖励、订阅续期迟到回调仍按原单对账并完成必要财务动作，不授予已注销账号业务能力。自动续费由渠道取消，不能在协议之外宣称注销自动关订阅。

重试采用退避、次数/时长上限及人工处理状态；账号始终不可用。对外不因内部清理重试宣称账号恢复。

中央提示owner置于退出后仍存在的根认证层，用一次性事件ID消费；页面重建不重播。业务门禁不能只存在将被dispose的账号页。受理成功后本地清理失败时阻止旧shell继续发请求，并允许重试原清理；重启后旧持久token必须由服务端拒绝。

验证码、短期凭证原则上仅内存；进程恢复需要查原操作时，仅保存账号/环境隔离的最小操作ID及必要安全查询凭证，短TTL、成功清除；不保存验证码。新账号不能消费旧查询结果。

## 8. 协议发布与版本

附件原文位于docs/legal/PhoneAgent账号注销协议.md，等文HTML为docs/legal/Phone_Agent_account_cancellation.html。发布稿仍标“待发布”，正式发布时更新版本标识并保留历史版本，不默默覆盖受理时合同。

建议沿用现有协议托管目录，但路径需发布后实测再配置。现有原生已有openPublishedAgreement，可由Dart协议端口复用以减少双端原生修改。打开失败停留原流程并给适用重试；阅读链接本身不授予提交、撤销或登录权限。

提交保存协议版本与内容摘要；服务端强制协议版本过期时重新展示确认，不自动勾选或自动提交。协议时间表述“15个自然日”与需求“连续15×24小时”需发布前统一，建议按详细需求采用连续15×24小时，最终正文调整应明确确认。

## 10. 验证方案

完整25项DEL见本change规格。除逐项验收，必须增加以下组合回放：

- 发送→离页→重进、错误码→过期、重复验证、旧账号回调迟到；普通登录验证码不能用于注销。
- 确认弹窗→协议→返回→取消，不发送短信；点击注销→发短信→验证→提交；验证过期再验证；协议更新要求重新确认。
- 提交commit后断网→查原操作→同一截止；commit前失败→明确未受理；查询失败保持未知，不能新建。
- 受理成功→存储清理失败→重试→原登录页一次中央提示；重启不恢复业务。
- 冷静期验证→关闭/保持→再次验证，原申请不变；连续点击继续登录只撤销一次。
