## ADDED Requirements

### Requirement: 支付失败保留安全且具体的原因
客户端 MUST 按受控错误码/原因区分短时支付频率限制、原单累计重试上限、支付结果待确认、会员履约处理中及网络/服务异常；购买入口和待处理弹层 MUST 使用一致的原因分类，不按错误文字包含“订单”进行覆盖。未知原因 MUST 保留安全兜底，不输出供应商原始错误或伪装为频控。

本批增量合同为 `COMMERCE_ORDER_MINUTE_LIMITED`、`COMMERCE_ORDER_HOUR_LIMITED`、`COMMERCE_MATERIAL_INTERVAL_LIMITED`、`COMMERCE_MATERIAL_LIMIT_REACHED`；保留原 HTTP 200 业务错误 envelope。前三者安全提示支付操作过于频繁，累计上限引导查询原订单且不承诺短暂等待恢复。旧 AC0006 保留模糊安全回退，旧 AC0005 和未知码不全局放行或解析 message。支付操作 HTTP 5xx 优先于响应内业务码投影为服务不可用；网络不可达单独提示网络异常，认证与账号异常不冒充网络或频控。列表/目录原 404 和加载合同保留。

#### Scenario: 短时频控与累计上限
- **WHEN** 服务端分别返回短时频控和原单重试次数上限
- **THEN** 前者提示支付操作过于频繁及稍后重试，后者明确次数达到上限并引导查询原单；不能对上限承诺短暂等待即可恢复

#### Scenario: 未知结果与服务异常
- **WHEN** 原单支付尚未知、已付未履约，或请求收到 502/网络异常
- **THEN** 分别展示结果确认中、权益处理中或服务暂不可用；有原单时保留查询路径，不因此新建第二笔付款或显示支付失败终态

### Requirement: Android 与 iOS 共用脱敏支付诊断
客户端 MUST 复用现有 CommerceDiagnostics 记录有效支付流程阶段、受控业务原因、耗时和脱敏订单/请求关联，关联现有实际安装版本与环境来源；不能只在 iOS 启用。诊断 MUST 不改变付款结果，不记录签名材料、Token、真实号码或供应商完整正文。

#### Scenario: 定位某次支付错误
- **WHEN** 当前账号在报价、下单、取材料、渠道返回或查单阶段失败
- **THEN** 可区分失败阶段和安全原因，并关联同一次订单/请求及安装/环境证据；未知错误有安全类别，写诊断失败不阻断原流程

### Requirement: 第7项定位与修复验收独立
R07 MUST 独立跟踪定位、失败回放、证据驱动修复、自动回归及真实运行验证。现有 ZIP 的 7 次 502 MUST 仅视为未关联接口的线索；没有同一次失败关联不得宣称现场根因确认，不得以文案变更完成 R07。

#### Scenario: 证据不足
- **WHEN** 只能观察通用支付提示或无接口路径/业务码的 HTTP 502
- **THEN** 记录已知现象、缺失信息和待排查分支，先补取证与失败回放，修复/运行验收任务保持未完成

### Requirement: 首单完成后可立即继续购买
在可信支付和履约均成功、无其他有效未决会员占位且未命中真实保护规则时，客户端 MUST 允许立即重新报价并继续购买同级、较高或较低等级会员，包含首单权益待生效的情形；不得要求等待旧订单 15 分钟期限。付款事实、材料和幂等身份 MUST 属于对应订单。

#### Scenario: 月卡购买成功后继续购买
- **WHEN** 月卡可信支付且履约成功，用户立即同级续购、升级或购买低级卡
- **THEN** 各自按当前权益取得新报价和独立订单，展示真实生效/排队说明，不误恢复已完成首单，不重复执行首单付款或履约

#### Scenario: 有效未决与迟到结果
- **WHEN** 首单付款待确认或已付未履约，或渠道回调/查询响应迟到、重进页和重复点击交错
- **THEN** 保留原单恢复和处理中门禁，不重复扣费；有效终态收敛后可继续购买，旧响应不覆盖当前操作或新账号

#### Scenario: 保留真实保护
- **WHEN** 实际命中下单限频、材料间隔、累计上限、活动租约或渠道校验拒绝
- **THEN** 按真实原因和适用恢复方式提示，不通过删除原单、清占位、取消频控或伪造成功让测试通过

### Requirement: 最后支付结果仍保留受控频繁原因
待处理购买与最后支付结果弹层 MUST 复用同一安全错误目录，不得在最终反馈中丢弃新频控码的安全原因。累计上限 MUST 同时说明支付操作频繁及本订单重试次数已达上限，并引导查询原订单，不承诺稍候即可恢复。成功、已付未履约及真实取消的优先级保持，未知正文不能冒充频控。

#### Scenario: 频控或累计上限后显示最后结果
- **WHEN** 真实 API 返回材料间隔或累计上限，用户从待处理购买继续支付，再进入最后结果弹层
- **THEN** Android/iOS 两端最终弹层与待处理弹层保留同一受控原因，累计上限同时出现频繁与上限/原单说明；不被统一替换成“本次支付未完成，请稍后重试”
