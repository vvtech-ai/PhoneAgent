## Goals / Non-Goals

**Goals:**

- 完整覆盖 R01～R08，并让每项有对应任务和可观察验收。
- 统一会员可见名称、等级标识与清晰点击区域；保留价格、原价、折扣、协议和排队说明。
- 让支付安全错误原因贯通到展示；R07 独立完成取证、失败回放、修复和验证。
- 由后端提供符合号码规则的推荐，指定门店例外在实时及恢复展示中一致。

**Non-Goals:**

- 已授权业务实施、相关测试及测试签名包；不包含安装、归档、部署或真实支付/外呼，推送按当次明确授权判断。
- 不改价格、限额数值、会员排序/计时/发分、渠道鉴权、定位权限流程或酒店搜索行为。
- 不全局替换商品快照正文，不另建会员/订单/任务状态机，不批量审计整个旧 App 的无关页面。

## Decisions

### 1. 按既有模块和独立规则接入

| 需求 | 拟涉及的文件或扩展点 | 职责与扩展方式 |
| --- | --- | --- |

| R04/R05 | `membership_balance_card.dart`、`membership_offer_header.dart` | 各自只处理积分卡布局、权益标签样式；流水行独立可点击，右箭头不单独缩小点击区域 |

### 2. 卡种名称与购买类型分离

1/3/12 月展示“月卡/季卡/年卡”；“1个月”等实际使用时长和时间单位保留。商品标题旁以蓝色小字显示“续购/升级”，整体语义分别为“月卡·续购”“月卡·升级”等。免费首次只显示卡种；当前权益未知时不猜测免费或升级。

只比较当前 ACTIVE 生效等级与目标等级：相同/更低显示续购，更高显示升级；不比较所选时长、暂停或排队套餐。购买后刷新当前权益，再更新标识。确认和履约仍以服务端 quote/result 为准，低级购买的真实 `LOWER_QUEUED` 类型及等待生效说明保留，不改成后端 RENEW。会员订单展示使用结构化字段格式化，不写回历史商品名；非会员商品名称保持原值。

### 3. 支付原因不能再按文案猜测

保留错误码和受控原因，移除页面按“含订单”兜底和弹层统一覆盖的展示机制。复用安全 allowlist，不直接输出服务端/供应商原始消息。下单频控当前用通用 AC0005，而 AC0006 将材料频率与累计次数合并；Java 配套任务先冻结可区分的增量原因，再由客户端映射。

短时频控提示“支付操作过于频繁，请稍后重试”；达到原单累计重试上限提示次数已达上限并引导查询原单；未知支付结果提示仍在确认；502/服务异常提示服务暂不可用。提示不能改变支付事实，已有原单必须保留可查询入口，不能因瞬时异常创建第二笔付款或自动再扣费。

### 4. R07 独立工作流与门槛

```text
确认安装版本/环境 → 补齐脱敏阶段及请求关联 → 重现失败并关联服务端
         → 区分频控/原单占位/支付或履约/租约/网关故障
         → 编写失败回放 → 最小修复 → 定向回归 → 运行与设备证据
```

定位组先覆盖 quote、create、material、native return、query、fulfillment 和 membership refresh，复用现有诊断事件与安装版本来源。只记录固定阶段、安全码、状态、耗时和脱敏订单/请求关联，不记录签名材料、Token、真实号码或供应商正文；失败后仍可查询原单。未知业务错误也应保留可定位的安全类别。

服务端默认 5 单/分钟、20 单/小时、原单材料累计 5 次、间隔 15 秒仅是源码默认值；原单 15 分钟期限不是正常首单成功后的购买冷却。先核对有效环境配置和原单事实。已有 claimMaterial 分离查单冷却的修复不得被重复当成现场结论。

修复组依定位结果决定是否需要 Java 或环境变更。验证组独立覆盖“支付且履约成功后立即同级续购/更高级升级/低级排队”，以及已付未履约、原单未决、真实频控、次数上限、502、迟到回调、重复点击、切账号和重进页；模拟成功不关闭真实渠道验收项。

### 5. 餐厅候选按意图区分

Java 在通用推荐的候选限额前过滤不可拨打门店，保留现有距离/类别/排序与必要的扩大范围搜索；避免先取前几家后才过滤导致假空列表。无有号结果时说明“未找到符合条件且有可拨打电话的餐厅”，不暴露被过滤门店为可选推荐，不编造号码。

明确指定餐厅且相关命中唯一门店时保留该真实无号门店，在候选中和文字说明中标识“暂无可拨打电话”，不说“没找到餐厅”，不要求先选中才告知。该候选不进入无号码的拨打确认，不自动换店；用户主动补充号码继续沿现有校验和确认。通用菜系、地区和附近关键词不能被误判为具体店名。

后端搜索响应、showOptions 归一化、实时 SSE 与账本恢复沿同一候选身份传递可用性；不在前端复制搜索过滤或重排状态机。定位拒绝时仍可指定城市/区域，授权后重搜、重复查询和任务恢复遵循原定位合同。Web 复核配置来源；共同任务合同若需增补，三仓完整同步相同文本，不只追加矛盾日期备注。

## Risks / Trade-offs

- 原因丢失与现场故障混同 → R02 文案修正和 R07 定位/修复/验证分开勾选，缺现场关联时只称机制确认。
- 仅修套餐卡仍泄漏旧名称 → 统一展示函数，覆盖结果、订单、套餐明细及旧快照显示，但不改历史事实。
- 一次性反馈在刷新/返回时重播或旧账号泄漏 → 绑定操作身份和账号代次，成功只在持久操作成功后触发，失败保留回滚和适用重试。
- 指定店名识别或过滤时机造成漏店 → 普通/指定、品牌/分店、全无号/混合/前部无号后部有号的接线回放。
- 窄屏、大字体误触或溢出 → 覆盖 320/375/430 宽及 1/2 倍字体，分别检查绘制区域、点击区域和真实回调；Android/iOS 画面另验。

## Migration Plan

先冻结兼容错误与候选字段，后分 UI、任务、支付、搜索微批实施，再运行受影响测试。新增字段允许旧响应缺失时沿原安全流程处理；新客户端不以缺字段推断号码可用或支付成功。无预设数据库迁移；环境修复另列实际目标、回滚方法和授权。界面回滚不撤销支付事实或已购权益，不回退其他已验收功能。

## 2026-10-21 用户现场复测补正

品牌多门店列表统一在候选上限前过滤无号，只有明确指定且相关命中唯一的单一门店保留无号说明；品牌名或 limit=1 不能单独开启例外。支付间隔及累计上限的安全原因必须贯穿最后结果弹层，累计上限文案包含“支付操作频繁”以及本订单上限和查询原单建议，不承诺短暂等待恢复。候选筛选留在后端，支付状态与保护阈值不变。

## OTA 任务反馈诊断追加

当前设备确认为此前交付的测试 APK，冷启动仍无任务操作提示；设置切模普通提示可见。现有包没有记录控制器发送及宿主门禁原因，先补任务模块内部固定阶段技术日志，再以同次设备操作定位，尚不修改业务门禁或宣称兼容性根因。独立 trace helper 只格式化白名单阶段与布尔值，控制器负责操作/反馈事实，宿主负责接收与页面可见性；不扩写共享诊断事件或通知队列，避免混入其他任务修改。诊断日志自身故障不得影响业务。
