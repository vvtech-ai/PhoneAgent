## ADDED Requirements
### Requirement: 登录协议与凭证必须一致
Flutter MUST 两端展示并强制同意协议后才发送验证码或登录，提示使用共用Toast；手机号变化清验证码和challenge；邀请码提交忙态不得返回。品牌标题保持现状，键盘按各端原生选择。
#### Scenario: 更换号码与协议拒绝
- **WHEN** 标准化号码改变或未同意协议提交
- **THEN** 清旧凭证或Toast阻止请求，冷却仍按发送号码绑定
### Requirement: 邀请草稿与入口生命周期必须分离
Flutter MUST 保存手工和外链邀请码，返回或继续仅消费欢迎入口；码变更清请求标识，同提交重试复用；登录成功清理，不持久化验证码/challenge。
#### Scenario: 返回并重启
- **WHEN** 欢迎返回后进程重建
- **THEN** 不重放已消费欢迎，保留邀请码并自动填入注册
### Requirement: 欢迎页必须匹配原生共同设计
Flutter MUST 共用品牌、积分、邀请码、原生文案和布局，前台重新校验；iOS原生失效业务错误白名单允许继续，其他错误主按钮重试，未知奖励不得当零。
#### Scenario: 失效或网络故障
- **WHEN** 邀请过期或请求网络失败
- **THEN** 分别允许继续登录或重新加载，均展示真实错误且不虚构积分
### Requirement: 初始化模型切换不得阻塞推进
Flutter MUST 保持两步并按Android异步发起模型切换，不等待结果推进身份或跳过保存；模型结果使用共用Toast，当前账号实际模型按服务端事实刷新。
#### Scenario: 模型迟到或失败
- **WHEN** 身份已保存且模型尚未完成或失败
- **THEN** 可进入首页，当前会话得到结果通知；旧账号响应不得污染当前状态
