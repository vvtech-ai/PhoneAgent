## Context

当前工作树从 `75e0e25` 创建 `codex/native-feature-parity-audit`，包含 iOS Team 配置，初始干净。参考根目录分别为 `/Users/Eason/Desktop/Git/AIAssistant1/android` 和 `/Users/Eason/Desktop/Git/AIAssistant/iOS`。原 `4c781e3`/`ddb996a` 及9月验收报告保留历史含义，不能冒充本轮三端同版本验收。

## Goals / Non-Goals

**Goals:** 按有效入口建立可追踪台账，区分源码接线、功能差异、平台限制和未验证状态；形成后续可执行任务及验收预期。

**Non-Goals:** 本 change 不实现邀请、SIP、可信来电或媒体能力，不重跑旧人工测试，不修改原生参考仓库，不归档尚未验收的 change。

## Decisions

1. 使用固定提交和仓库相对路径记录证据。外部源码以 A/I 根别名定位，执行 `git show <sha>:<repo-path>` 可重查；Flutter 采用相对 Markdown 链接。目录卡片或类名不能单独证明入口可达。
2. 每项使用 NF 编号；原 P01–P29/P08a 保留。实现状态与自动/真实接口/真机证据分别记录，不计算“通过百分比”。历史报告只证明其日期、提交和列出的场景。
3. 六类场景是后续验收预期，不是本轮测试结果；平台特有的权限、后台、中断、冷/热启动、升级另列。原生行为有冲突时，记录差异及决策问题，不自行推断一端更权威。
4. 新目标覆盖指定原生工程有效能力。历史排除的 SIP、可信来电等进入后续能力设计；这不等于步骤一已批准所有实现细节。旧独立页面按业务效果映射到统一页；没有有效入口证据的快捷输入、支付、记忆不凭文件或文案自动扩展。
5. 现有能力优先延续当前 active change；没有匹配 change 的缺口给出建议 ID 和依赖，但本轮不创建空的业务 change。iOS 手动版本检查先核实入口，若后续证实有效，其外部更新也与 Android APK OTA 分开，后台声明与实际后台可用分开。
6. 台账作为新版差异事实源，原页面覆盖表增加对应索引，不复制历史日志。本轮文档按不超过3文件的编辑微批推进，最后统一同步任务与问题记录。

## Risks / Trade-offs

- 静态审查不证明后端、SDK和硬件成功：未知字段、无法确认的入口和权限效果明确待核实。
- 参考工程持续演进：固定完整 SHA，后续版本差异独立增量登记。
- 现有需求与新目标冲突：需求文档保留既有运行基线并标注目标扩展；delta spec 在验收归档前不覆盖正式 spec。
- 外部本地路径不便跨机器使用：提供根映射、提交及仓库相对路径，不依赖当前分支名称重现。

## Validation

运行 `openspec validate --all`、`git diff --check`，检查新增文档本地链接、引用的三端源码路径、NF/P 编号覆盖和六类场景完整性。仅文档，不运行 Flutter analyze/test 或双端构建。工具不可用时记录实际失败及原因，不把自制格式检查当 OpenSpec CLI 通过。
