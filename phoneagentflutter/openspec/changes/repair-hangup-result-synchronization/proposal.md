## Why

禅道问题 23772、23773、23678 的客户端诊断都显示请求大多成功，并且在物理通话结束或异常中断后仍收到 Agent/SSE 事件；其中多份诊断已经出现 `finalResponse`、`batchCallResult` 或 `committed`。截图却显示会话页、任务列表或批量结果卡仍停留在加载、未读或未完成状态，重新进入会话后结果又可以出现。220 test 日志已确认 23772、23773 的后台结果写入顺序；23678 的对应历史归档未命中，积分不足错误码仍待确认。

当前 Flutter 代码在物理终态后只进行有界的历史结果同步，部分异常挂断终态不满足 `needsAgentOutcome()`，且单路终态没有统一触发任务列表失效/刷新。23772、23773 日志出现 `RUNNING -> INCOMPLETE` 中间投影后才提交最终批量结果，页面可能在这个窗口停止观察；重新进入页面会再次读取历史，因此形成“后台有结果、当前界面无反馈”的时序窗口。本变更保留后台结果未确认分支，避免把 SSE done、物理挂断或传输失败误判为业务成功。

## What Changes

- 2026-10-21 本地修复范围：补齐同一会话在前台/路由返回、断网恢复时的只读补查；单路已知 callId 和尚无 callId 的结果观察分别设置独立五分钟截止时间，慢请求不能无限延长等待。SSE 在单路注册 callId 前遇到未知 502/503 握手失败时保留执行不确定性，按当前确认 command 有界读取账本，只接受同命令的已提交执行异常终卡；未取得结果则反馈未确认，不自动重拨。多路后段轮询改为 10 秒且保留独立五分钟截止，进度/账本请求尚未返回时到点也须反馈。网络事件共享一个平台订阅；日志级别由构建配置选择 DEBUG/INFO/WARN/ERROR，握手诊断只携带受限 HTTP 状态码。本地回归已通过，真机验证待补。不新增系统电话状态权限。
- 审查补充的单路边界：旧物理闭合通话结果超时后停止本地状态轮询，新拨号工具须再次由用户确认，旧 call/attempt 留待只读补查；旧执行或物理闭合尚未确认时，新工具给出待核提示，避免呈现无法执行的确认卡。`call_finished` 只作为同 attempt 或当前确认 command 的结果读取线索，不作为物理闭合或业务成功证明。
- 证据边界：此前诊断 ZIP 只见 HTTP 502/500，未见 503；本轮没有可关联的 2026-10-21 dev 来电会话 session/完整服务时序。旧包和源码回放不能证明当前 dev 现场的服务端提交时刻或真机终卡效果，按 4.3 另验。
- 2026-10-20 本次真实批次补充：当已提交回执为 `PENDING / EXECUTION_ERROR` 时，当前会话以该权威回执替换同 batchId 的临时进度卡，并记录回包、账本同步和页面可见结果的脱敏诊断；缺失的通话和账务证据保持待核对。
- 单路已提交的 `EXECUTION_ERROR` 是任务执行终态，结果卡显示“执行异常”，不能再渲染为“结果确认中”。简短的公开业务说明可以显示；任务卡不展示内部诊断或技术码。通话业务成败未知时仍保留未知语义，不据此伪造未接通或零扣费。
- 单路已收到可信的 `CALL_OUTCOME_REPORTED.outcome=UNCLEAR`，或同身份非运行最终结果的 `status=UNCLEAR`／`agentOutcome=UNCLEAR` 时，业务报告已经到达，不能再画黄色“结果确认中／结果未确认”终卡：任务型显示“任务未完成”，普通电话显示“通话未完成”，状态均为“未完成”。仅有物理完成而没有业务报告时参照 v66.0.3 显示独立的黄色“正在确认通话结果”小提示，不生成结果卡；有界观察结束仍无可信结果时显示待核实反馈，保留原身份供补查。同一 session 与 callAttempt 的后续已提交结果可以补齐终卡业务字段、简短业务说明和已确认账务，不能被较早的语义报告整体遮蔽；三类事件的 `commandId` 各有来源，不要求相等。禅道 #23809 的单路订餐是验收样本：220 test 账本已报告 `UNCLEAR`、任务投影为 `INCOMPLETE`，随后提交最终结果且客户端读到对应序号；持久结果无 `sceneType`／`resultCode`，`detail` 为通话转写，长语义原因在 `agentReason`。保留未获明确订位确认和短信发送未确认等原事实供状态判定与诊断，不把未知预订改写为成功，也不把长诊断放进任务卡。
- 本轮交互口径补齐：单路已提交 `callResult.status=COMPLETED` 若缺可信 `CALL_OUTCOME_REPORTED` 或明确的 `agentOutcome`，仍等待业务结论；`resultCode` 单独不足以结束等待，不能把处理完成当绿色终卡。多路五分钟截止仍无已提交终卡时保留“结果尚未确认”的临时进度，不画“执行结果／结果回传”终卡。可信完成显示绿色终卡，可信失败、未完成或执行异常显示红色终卡；有界观察截止不强行推断红绿，原身份留待只读补查。
- 当服务端执行异常发生在拨号或批次结果恢复前，回执可能没有 `callAttemptId`，或只有空 `items` 且没有 `batchId`；当前轮仍需以 command 身份展示执行异常终卡，历史以提交事件恢复，未知逐路事实与非终态账务保持待核对。

- 为异常挂断、网络异常、积分不足和多路通话结束建立统一的“物理通话终态→结果事实同步→页面解除 loading”流程。
- 在物理终态不满足现有 Agent outcome 条件时，继续以会话/尝试身份进行有界、可恢复的历史结果读取；结果已出现时立即合并消息并结束加载状态。
- 单路与多路结果到达后统一触发任务列表失效/刷新，确保未读、完成度和结果卡与后台事实重新对齐。
- 明确区分业务结果、业务失败和传输/挂断信号；SSE done、物理 hangup、网络断开或积分不足提示本身不得被提升为业务成功。
- 在客户端诊断中补充稳定的 sessionId、taskId、callAttemptId、同步阶段和最终判定字段，便于与后台日志关联；不记录对话正文、令牌或敏感凭据。
- 后台日志核对已使用 220 test 真实服务日志完成 23772、23773 的时序确认；23678 未取得对应回包，不改变后端协议或声称积分不足根因已确认。

## Capabilities

### New Capabilities

- `hangup-result-synchronization`: 异常挂断后结果事实、页面状态和任务列表的一致性。

### Modified Capabilities

- `conversation-error-status-sync`: 补充异常挂断与结果落库时序下的终态同步边界；不改变普通退出、异常恢复命令或外呼控制语义。

## Impact

涉及 `ConversationCallController`、会话终态/结果流编排、历史结果读取、批量流生命周期、任务列表 provider 失效与可观测诊断字段；可能需要补充针对单路、多路、网络异常和积分不足终态的 Dart 定向测试。预期不新增依赖、不修改后端接口契约和数据库结构。后台日志查询需要明确问题对应环境以及结果/SSE、任务/历史、通话运行态服务的真实模块后再执行；当前已保存的客户端诊断仅作为客户端证据。验证包含 `openspec validate --all`、受影响模块静态检查和定向测试，真机断网/异常挂断场景另按授权执行。
