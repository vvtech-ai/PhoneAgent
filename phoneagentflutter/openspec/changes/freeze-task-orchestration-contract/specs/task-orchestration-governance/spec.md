## ADDED Requirements

### Requirement: 任务编排修改必须遵循同版本共享合同
Flutter 研发 MUST 在修改任务入口、消息、思考 / 工具、确认、结果、评分或 TTS 前读取本仓 AGENTS 的完整 `task-orchestration-v1.3` 及本仓任务编排知识库，按当前用户决策和回放编号确定行为。三端共同规则 MUST 同版本同内容，不依赖相邻仓库或个人目录；长期规则 MUST 与批次进度分开。历史相反条款 MUST 标记替代，不得通过最新日期备注或旧测试通过数反转合同。

#### Scenario: 新修复与历史规格冲突
- **WHEN** 实现者遇到清理本地消息与保留已显示业务内容的相反要求
- **THEN** 使用当前合同，限定临时进度清理身份，保留旧卡快照和正文，并为实际修复另建 change

### Requirement: 首页联系人与任务列表共用身份和结果规则
首页与联系人 Skill 新建 MUST 冻结入口快照和选定对象；列表恢复 MUST 复用原 session / task / attempt，历史详情 MUST 只读展示原事实。同任务在各入口的消息顺序、媒体锚点、模型评价和任务评分 MUST 一致；联系人系统拨号与翻译保持各自路径。

#### Scenario: 联系人选择后配置迟到
- **WHEN** 用户选择联系人和 Skill，后续首页配置或旧弹层回调到达
- **THEN** 当前任务的姓名 / 目标号码 / Skill / 专用开场不被覆盖，账号或入口已变化的回调不创建任务

#### Scenario: 从任务列表恢复或查看结果
- **WHEN** 用户进入已有会话、单通 / 批量结果或无账本旧详情
- **THEN** 复用原任务身份与可信内容，不重播开场、不自动拨打、不复活旧确认；结果 / 评分与实时页共用语义，缺失历史不得伪造

### Requirement: 冷启动入口以完整快照解耦后台刷新
入口 MUST 优先使用有效缓存，无缓存时使用经确认随包快照；卡片、Skill 和开场 MUST 一致且完整，明确无开场的入口除外。后台刷新 MUST 只影响下次进入，不增加常规任务内加载重试或等待会员展示的整页门禁；缓存不授予当前权益。

#### Scenario: 首页或联系人抢先进入
- **WHEN** 远端配置尚未返回而用户选择有效任务入口
- **THEN** 使用完整快照展示一次正确开场，道歉使用专用 Consent，实际模型与准入继续真实检查，不因迟到配置丢失、改写或重复开场

### Requirement: 结果评分和播报必须连续验收
后续实现 MUST 按合同覆盖同身份原位补全、不同操作独立追加、原确认正文保留、评分晚就绪与失败恢复、历史不重播 / 重拨。只调用单个加载函数或只比较消息数量 MUST NOT 代替真实控制器连续回放。

#### Scenario: 结果先到评分资格后到
- **WHEN** 原任务结果已经可见，后续终态或资格补全
- **THEN** 在原区域补评分，不要求退出重进、不阻塞结果和 Agent 说明，未知 / 失败不被永久当作无资格

#### Scenario: 文档验收结束
- **WHEN** 本 change 的 OpenSpec、链接和编码校验通过
- **THEN** 仅标记规范交付，业务修复、连续回放、后端和设备状态继续分别记录

### Requirement: 记忆使用语义判断与原信息补问流程一致
自由回答 MUST 参照确认拨打的语义判断方式识别当前记忆使用意图，只有明确同意才采纳；账号、当前绑定 Skill、候选版本与 pending 身份仍由确定性规则校验。不同意、不明确、疑问、修改或判断失败 MUST 在本任务中停止使用询问，转回原有信息收集；新任务重新确认。结构化明确选择保持确定语义，已提交语义决定恢复时不得重新分类；使用不代表写入或拨打授权。

#### Scenario: 用户没有明确同意使用记忆
- **WHEN** 用户拒绝、不明确、改用本次信息，或语义判断失败
- **THEN** 本任务不采用记忆、不因新候选反复询问，直接补问本次信息；普通无记忆、保存、联系人和拨打流程继续遵循原规则
