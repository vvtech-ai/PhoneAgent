# 任务结果已读确认修复

## 需求来源

禅道 Bug 23772。session `c7d808a316533029244458d794917bb0` 在 test 220 已完成批量结果投影并发出 `task_completed`，但服务器 SDK 日志未观察到对应的 `AGENT_CONVERSATION/{sessionId}/read` 请求。当前客户端已读异常被静默吞掉，导致无法判断是未触发还是请求失败，任务列表可能继续显示未读红点。

## 已确认事实

- 后台在 `10:44:01.630` 将会话从 `RUNNING` 投影为 `INCOMPLETE`。
- `10:44:01.707` 提交批量结果，`10:44:01.717/1.718` 发出 `task_completed`，`10:44:02.184` timeline 读取到序列 53。
- 对 test SDK 日志按精确 session 查询返回成功但无对应任务已读请求；该结果不能证明客户端绝对未发请求，因为没有客户端 HTTP 抓包。

## 修复范围

1. 修正批量终态识别：后台对需关注的结果返回 `status=PENDING`，执行结束通过 `executionStatus=FINISHED` 表达。客户端此前丢弃执行状态，显示结果后仍跳过已读请求。
2. 明确执行完成且页面可见时发送已读 PUT；运行中、未带完成字段的 PENDING、账号切换或页面不可见不得触发。旧版无执行字段的明确终态保持兼容。
3. 将固定阶段诊断接入现有账号 journal，不依赖 assert；日志异常不得影响请求和重试。
4. 不改任务列表 API 路径、后台业务源码或其他结果观察变更。源码缺陷已同构复现，原设备实际 payload 和完整 API 序列仍待确认。

## 验收标准

- `INCOMPLETE`、`FAILED`、`UNCLEAR` 等终态可触发已读确认；`RUNNING`/进度不触发。
- `PENDING + FINISHED` 的 FAILED/UNCLEAR 批次在实时展示和历史恢复时均触发已读；PENDING 业务含义不变。
- 已读失败后不伪造成功，重新可见或应用恢复仍可重试。
- 诊断只包含 sessionId、阶段、固定结果/错误类别，不包含正文、号码、token 或凭据。
