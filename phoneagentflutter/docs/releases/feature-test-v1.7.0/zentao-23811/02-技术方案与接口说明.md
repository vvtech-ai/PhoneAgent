# 技术方案与接口说明

## 本地修复

- 旧现场同批 `PENDING / EXECUTION_ERROR` 已由服务端提交，进度序号和 timeline 均到 27；此前“旧进度卡可覆盖已提交回执”是另一条已由源码与合成回放确认的结果合并缺口。本轮处理的是**尚无可信业务结果时**的黄色卡／临时进度展示，不能用该分支解释旧现场为“后端未产出结果”。
- `NativeCallReceiptPresentation` 将缺少可信语义结果且无明确技术异常的单路完成状态保持为 `physicalResultPending`，由正式会话入口显示整理／待核实文字；已可信 `UNCLEAR` 和执行异常仍进入对应红色终卡。既有明确技术异常可先显示红色异常反馈，语义结果观察仍依其独立门禁运行。
- `ConversationCallController.acceptReceipts` 与 `ConversationResultObservation` 在结束同一通话观察前校验合法的语义 `agentOutcome` 或明确的失败／未完成／执行异常状态；物理状态、已提交标记、`PENDING`／未知 outcome 及单独的 `resultCode` 不能关闭观察。原有 command、callId、attemptId 归属校验继续生效。
- `BatchProgressTracker` 在观察窗口耗尽时以本地 `VERIFYING` 标记未决批次和逐路项。`BatchReceiptCard` 维持进度卡并明确显示“结果尚未确认”，不将本地待核快照渲染为“执行结果／结果回传”终卡；真实已提交回执仍按现有规则原位替换。

## 接口与兼容

不新增或改变后端 API、事件字段、持久化结构或账务计算。`VERIFYING` 仅用于客户端临时进度投影，不作为服务端业务终态。已知逐路成功或失败事实保留；未知路继续待核，不补造扣费或结论。

单路和多路自动观察继续受现有五分钟截止约束。截止后保留原身份供页面恢复或网络恢复时只读补查；客户端不能保证服务端一定提交终态，因而不能以超时替代红／绿终卡。

## 回滚

若本地展示回归，回退上述单路等待准入和批量临时进度投影的本轮代码改动与对应测试即可恢复先前客户端行为；没有数据迁移或服务端回滚步骤。回退会重新暴露黄色结果卡和未确认批次被误画为终卡的风险。
