PhoneAgent Architecture

Full-Stack Architecture and Open-Source Boundary

This document follows a phone-agent task from the Android client through the hosted backend to SIP/PSTN, remote models, SMS, maps, identity verification, and storage. It also defines exactly which components are included in this public repository.

Android: Kotlin + Jetpack Compose Backend: Java + Spring Boot HTTP / SSE / WebSocket SIP / RTP / WebRTC Verified against the current codebase

1. System overview

The system consists of an open-source Android client, a non-public hosted backend, and external communication and AI services. The client owns interaction and device capabilities; the backend owns accounts, Agent orchestration, task state, and telephony coordination.

2. Android client architecture

The client does not hold production model keys or SIP accounts. It captures user intent, obtains confirmation, invokes hosted contracts, carries authorized real-time media, and presents results.

UI layer

  • Jetpack Compose screens and navigation
  • UiState / UiAction / UiEffect
  • Permission guidance, confirmation, and results

Domain layer

  • Task, number, contact, and receipt rules
  • Call, translation, and voice state transitions
  • Use cases, coordinators, and policies

Data layer

  • Retrofit HTTP APIs and SSE Agent streams
  • WebSocket audio and real-time events
  • Repositories, DTOs, mappers, caches, and logs

Integration layer

  • Contacts, call log, camera, microphone, and OTA
  • LiveKit, Volcengine RTC, and SIP/WebRTC audio
  • Bundled CHAKEN trusted-call SDK

3. Hosted backend architecture

The current hosted implementation is a Java/Spring Boot service using Spring MVC, WebSocket, JPA, Redis, MySQL drivers, and JAIN SIP. Its source is not included in this repository.

Traceability: events across the client, Agent, SIP, model, and media bridge should carry traceId, sessionId, taskId, callId, provider, and state transitions so that modules do not maintain competing sources of truth.

5. Core workflows

5.1 Agent phone task

1. Describe the needVoice or text input
2. Agent understandingHosted model and built-in Skill/tools
3. User confirmationNumber, time, recipient, and content
4. Call executionSIP account pool and real-time model
5. Result deliverySSE/HTTP → transcript, receipt, and history

5.4 Multi-party meeting invitations

The Agent splits contacts into independent calls. Within the configured concurrency limit, the backend leases a SIP account, creates a model session, and maintains a distinct callId for each call. Effective concurrency depends on SIP-account count, route policy, multi-registration support, backend limits, model quotas, and public media reachability.

6. Data, credentials, and security boundary

Data the client may store

  • Sign-in and refresh tokens
  • User settings, model/voice preferences, and local caches
  • Authorized contact and call-log results
  • Redacted client diagnostics

Data that must remain server-side

  • Model API keys and secrets
  • SMS secrets and template credentials
  • SIP usernames, passwords, pools, and routes
  • AMap Web Service keys, database secrets, and object-storage secrets

Client authorization parameters for the CHAKEN trusted-call SDK are explicitly approved for distribution with the open client. Values embedded in an APK remain extractable, so they must be revocable, least-privileged, and client-scoped. They are not production backend secrets.

8. Future position of Call Skills

A Call Skill is intended to sit between user intent and backend call execution, standardizing scenario inputs, confirmation, dialogue policy, tools, permissions, and result schemas.

User intent“Book an appointment…”
Skill matchingScenario and compatibility
Input and confirmationSlots, permissions, and risk
Constrained executionDialogue policy and tools
Structured resultSuccess, failure, handoff, and receipt

Current status: the open-source client does not contain a Call Skill runtime. A future release will still require backend capability negotiation, safety review, version compatibility, and telephony authorization. A Skill file alone cannot bypass real-call boundaries.

Continue with the Call Skill vision and project roadmap.

Production deployment must verify HTTPS/WSS, SIP signaling, RTP ports and NAT, firewall rules, account-registration concurrency, and provider quotas. The code proves the integration shape; it cannot prove SIP-provider routing rights, concurrency policy, or public firewall access.
